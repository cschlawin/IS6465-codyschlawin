# Peer Tutoring Hub Application Builder

## Purpose

Implement approved Peer Tutoring Hub requirements through small, understandable changes to the existing application.

Help IS 6465 students understand how business requirements become working PHP and SQLite code.

## Project conventions

## PHP runtime compatibility

This skill targets PHP 8. Before writing or revising PHP, verify the installed runtime with `php -v`.

- If the project runs on PHP 8.0 or later, PHP 8 features such as union types (for example, `array|false`) are permitted.
- If the project runs on PHP 7.x, do not introduce PHP 8-only syntax. Preserve behavior with PHP 7-compatible declarations; for a function that may return either an array or `false`, omit the return type rather than changing `false` to `null`.
- When the runtime version is unknown, ask the user to run `php -v` or use PHP 7-compatible syntax until the version is confirmed.

After each PHP change, lint every changed PHP file with `php -l <file>`. Do not claim the implementation works until the changed files pass linting in the target runtime.

Use the existing project structure:

- `php/` — application PHP files and related folders
- `php/includes/` — shared templates and validation helpers
- `php/config/db.php` — reusable PDO connection
- `php/repositories/studentPDO.php` — student database operations
- `php/repositories/requestPDO.php` — tutoring request database operations
- `php/services/requestService.php` — validation and business workflows
- `php/tests/` — PHP tests
- `database/` — SQLite database and setup SQL

Preserve existing pages, including:

- `request-form.php`
- `process-request.php`
- `request-details.php`
- `requests.php`
- `edit-request.php`
- `update-request.php`
- `delete-request.php`

Inspect actual supplied files before making changes. Do not assume that every listed file already exists.

## Database requirements

Preserve the existing two-table design.

STUDENTS:
- student_id — primary key
- student_name
- student_email — unique

TUTORING_REQUESTS:
- request_id — primary key
- student_id — foreign key
- course
- topic
- preferred_date
- preferred_time
- status — default Open
- created_at

One student may have multiple tutoring requests.

Do not rename columns, add tables, or replace the approved database design without explicit approval.

## Existing interface requirements

Preserve the Lab 4 form controls:

- Course dropdown
- Multiple topic checkboxes
- Preferred date
- Preferred time radio buttons
- Reason textarea

Preserve student name and email fields added for Week 7.

The Week 7 implementation stores the selected topics and written reason in the existing `topic` database column using a documented JSON text convention.

Inspect the existing serialization and decoding functions before changing them. Preserve compatibility with existing saved records.

Do not silently replace checkboxes with a single text input.

## Architecture rules

1. Keep HTML and Bootstrap presentation in page files.
2. Keep SQL and PDO operations in repository files.
3. Keep business validation and transaction coordination in service files.
4. Keep database connection configuration in `config/db.php`.
5. Pass a PDO connection to reusable repository and service functions.
6. Use prepared statements for submitted values.
7. Enable SQLite foreign key enforcement.
8. Encode untrusted text before displaying it in HTML.
9. Use POST for database-changing operations.
10. Preserve existing working functionality.

Use procedural PHP appropriate for an introductory web application development course. Do not introduce a framework or unnecessary abstraction.

## UC01: Request Tutoring

Support the following behavior:

- Validate required inputs on the server.
- Validate student email.
- Find or create a student using the unique email.
- Create a tutoring request linked to that student.
- Store the new request with Open status.
- Display the saved request and its ID.
- Allow valid revisions to Open requests.
- Cancel an Open request by changing status to Cancelled.
- Retain cancelled records.

Coordinate related student and request writes in a transaction.

Rollback if the complete operation fails.

## UC02: View and Filter Requests

Support:

- View all saved requests.
- Filter by course.
- Filter by status.
- Combine optional filters.
- Display student information using JOIN.
- Display a helpful message when no records match.

Do not introduce new database tables for UC02.

## Development workflow

### Step 1: Read requirements

Identify the use case, requirement IDs, business rules, and acceptance criteria.

If required information is missing, identify the gap rather than inventing a business rule.

### Step 2: Inspect existing code

Review the relevant PHP files, database schema, and form field names.

Check the runtime PHP version before selecting language features. Match the implementation to that version and identify any existing incompatible syntax before testing the feature.

Determine what already works.

### Step 3: Plan changes

Identify the smallest coherent set of changes.

Explain which files need modification and why.

### Step 4: Implement

Generate complete code for the affected files.

Preserve existing names, interfaces, and unrelated behavior.

### Step 5: Explain

Explain how information flows through:

Browser → PHP page → Service → Repository → SQLite

Use clear language suitable for beginning PHP students.

### Step 6: Review

Check PHP-version compatibility, validation, SQL parameters, database constraints, output encoding, and error handling. Run `php -l` on each changed PHP file and report the actual result.

### Step 7: Recommend tests

Identify positive, negative, and regression tests.

Do not claim a test passed unless it was actually executed.

## Required output

Provide:

1. Requirements being implemented
2. Assumptions or missing information
3. Files to create or modify
4. Complete changed code
5. Explanation of important changes
6. Requirements-to-code mapping
7. Testing instructions
8. Remaining limitations

## Security boundary

Week 7 is a classroom application.

Do not add authentication, authorization, or session management unless specifically requested.

Explain that the current application is not suitable for public deployment without additional security controls.

## Student learning principle

Do not simply produce code.

Explain why each important file or function exists and how it satisfies a business requirement.

Encourage students to inspect, execute, and verify the generated implementation.
